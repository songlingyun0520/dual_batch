双 Batch 拆分后，SFA 为什么没有变快？

B4 的注意力计算被拆为两次顺序执行的 B2。MAC 与部分搬运指令时间近乎减半，但单次 SFA task 墙钟时间仍约 105 µs，导致每层 SFA 约多 103.50 µs。本页列出 61 层全部可对齐区间、算子差额和测量边界。

先区分“计算量”与“task 时长”

完整 B4 每层调用一次 SFA；拆分后依次调用 A0、A1 两个 B2 SFA。两组输入的 query 首维分别为 4 和 2，稀疏索引分别为 4×1×2048 与 2×1×2048，单条 query 的 2048-token 历史 KV 前缀没有缩短。两种形状的运行 block 数均为 24。

这些指标能说明什么

  1. MAC 和 MTE2 指令时间确实近乎减半，说明减少的算术与搬运工作在 profiler 中可见。
  2. 理论 AI Core 时间只下降约 28.5%，Scalar 时间只下降约 13.3%；单次 task 总时长仅下降约 1.6%。较少的工作主要表现为利用率下降。
  3. 完整 B4 可在一次 task 中处理多条 query；拆成两个不能重叠的 B2 task 后，总时长约为 210.47 µs，比一次 B4 多 103.50 µs。
推断与边界：每条 query 的稀疏访问长度不变，24 个运行 block 不变，SFA 的单次关键路径没有随总 MAC 数量对半缩短。现有计数器无法精确分解 block 调度、标量控制、核内同步和离散 KV 访存延迟各占多少。这里的 105 µs 是 Task Duration，不是纯 MAC 时间，也不是 Python/eager 逐算子提交时间。

华为 CANN profiler 字段定义：Task Duration 包含调度至加速器、执行与响应结束；aicore_time 是假定各 block 同时开始且执行时间相同的理论时间，不能用两列之差直接计算调度开销。

其余增量来自哪里

61 层平均的层内区间增加 248.74 µs：Indexer +32.67、SFA +103.50、其他 kernel +100.77、相邻 kernel 间空档 +11.80 µs。拆分实现对两组分别执行 Indexer 的前后处理、索引 cache 写入，随后还合并两个 SFA 输出。额外工作位于串行关键路径。
