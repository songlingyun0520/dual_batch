主表均为扣除适配开销后的值。MoE 层指含 attention 的完整 decoder 层；吞吐只计有效 batch。TPOT 是时间线校正估算，原始实测与扣除项见下表及 CSV。

实验结果分析

1. 没有额外 IO 时，当前串行拆分路径增加了开销。 14 个配对组合中，拆分后的校正 TPOT 均更高，增加 10.28～19.37%；有效吞吐下降 9.32～16.23%。完整 MoE 层平均新增 192.38～316.39 µs/层。当前 A/B 按顺序执行，没有实际 IO 重叠；拆分本身增加了分组执行和结果合并等工作，不能仅因分成两组就预期加速。

2. batch 增大提高总吞吐，但拆分代价并非单调下降。 在各输入长度的可运行范围内，两种模式的有效总吞吐均随 batch 增大而提高，同时 TPOT 也增大，体现吞吐与单请求时延的取舍。batch 8/10 的拆分 TPOT 增幅为 18.06～19.37%，batch 32 为 10.28～10.98%；但 batch 64 的已完成组合又增至 13.36～13.78%。因此不能把“batch 越大，拆分越划算”作为一般结论。batch 10 使用容量 12，执行成本含两个 padding，吞吐只计 10 个有效请求。

3. 输入变长主要拉长了 A 窗口中的 Indexer 部分。 以 batch 32 为例，输入由 8K 增至 32K，不拆分/拆分 TPOT 从 109.52/120.78 ms 增至 120.87/134.14 ms；A 窗口从 191.77 增至 303.43 µs，其中 Indexer B 从 58.02 增至 150.81 µs。B 窗口则仅从 299.32 变为 301.67 µs。这与当前实现中 Indexer 读取全长历史、SFA 只读取固定前 2K KV 的结构一致；不能据此推断完整历史 attention 的长度扩展性能。

4. A/B 窗口提供潜在 IO 掩盖空间，但不是已实现的加速。 两段窗口在当前时间线上不重合，可直接相加；总窗口为 435.09～714.09 µs/层。扣除拆分新增层时延后，逐层潜在净收益为 154.03～397.71 µs。cache 写入/QW 包含 Indexer 的缓存写入、投影和 RoPE；完整 batch KV/Q 则为 SFA 准备 attention KV 与 Q，均不是整段 CPU→NPU 加载时间。若后续优化这些计算阶段，其可供 IO 重叠的窗口也会变化，需要同时重新测量窗口和层时延。

5. 按全部 61 层加入 IO，完全掩盖时的理想吞吐提升为 9.43～17.62%。 本估算使用每层加载耗时 W=A+B，不拆分 TPOT 增加 61W/1000 ms，拆分 TPOT 保持原值。当前已测范围内最大比例收益出现在 32K、batch 32：不拆分串行 IO 吞吐 202.81 token/s，拆分理想吞吐 238.55 token/s，提升 17.62%。这是所设 IO 预算下的理想上限，未执行带 IO 的新 benchmark。各组合 W 不同，所以横向比较并非固定 IO 耗时条件；前 3 个 dense 层也套用同一个 W，尚未验证其真实可用窗口。

6. 实际部署需要先覆盖拆分本身的开销。 在同样的 61 层等加载耗时模型中，令 I=61W/1000 ms、h 为整步 IO 被掩盖的比例，则拆分带 IO 的 TPOT≈T拆分+(1−h)I。相对不拆分串行 IO 获益，需要 h>(T拆分−T不拆分)/I。本组数据的收支平衡掩盖比例为 35.95～62.79%，各组合门槛不同。该推导仍假定没有额外同步开销和计算减速；真实 IO 还必须分别适配 A/B 窗口、满足数据依赖，并避免带宽或计算资源竞争。

7. 数据覆盖与适用范围。 30 个条件中 28 个成功，32K、batch 64 的两种模式均在初始化时 OOM，不能外推其性能。每个成功条件保留 16 个稳定 decode 步、928 个 MoE 层样本；配对输出 token 一致，两个连续 TPOT 窗口的最大相对差异为 0.17%。这些窗口不是独立重复实验，不能作为置信区间。结果来自单张 910B2、BF16 dummy 权重 shape demo；适配开销扣除是时间线校正，首次 D2H 中不可独立分离的同步开销保守保留，不等同于真实权重、实际 IO 或多卡部署结果。

方法与复核

实验口径
硬件：本容器可见的 1 张 Ascend 910B2，64 GB HBM；TP=DP=EP=1。
模型：当前 61 层 BF16 shape demo、dummy 权重；256 个逻辑 expert 映射到 8 个共享物理 expert。
真实 Lightning Indexer 读取全长索引缓存；SFA 使用固定前 2048 KV。这不是 910C 的最近 2K 环形 KV，也不是真实权重精度或量化多卡部署的性能。
输入 token 数为 8192、16384、32768；每请求生成 160 token，temperature=0，ignore_eos=true，无前缀缓存。
第 i 个请求使用 token ID 110+i 重复组成输入；调用 completions 接口，无聊天模板额外 token。
有效 batch 为 8、10、24、32、64；图容量分别为 8、12、24、32、64。只在纯 decode 使用 FULL_DECODE_ONLY 图。
拆分按图容量等分：4+4、6+6、12+12、16+16、32+32；batch=10 时第二组为 4 个有效请求加 2 个 padding。
两组按既定顺序串行执行，没有 DBO，也没有 CPU KV 搬运。

时间测量
采样客户端与服务均在容器内，通过 127.0.0.1 HTTP 连接；不包含 SSH 或外网传输时延。
未开启 profiler 时取输出 token 16 到 token 80 的 64 个间隔；两个连续 32 间隔窗口用于观察稳定性，不冒充独立重复实验。
同一请求后段在所有请求至少生成 96 token 后开启 profiler，至少 112 token 后停止；只接纳结构完整、进入稳定平台的 decode 步，不把 profiler TPOT 当作客户端实测 TPOT。
所有有效请求在稳定区间前已经结束 prefill，区间内均未退出；padding 不计入吞吐分子。
完整 MoE decoder 层取第 3～60 层（0-based），包含输入归一化、attention、输出投影、MoE 和层末尾。CSV 中保留 MoE 子模块时延，边界为 attention 后归一化开始至层末尾。
普通层边界取本层输入归一化开始到下一层输入归一化开始；最后一层止于实际末尾 Add 完成，不补估计间隙，不纳入 LM head 或采样。
CANN 图可能在层内部切换底层 stream。分析按依赖顺序跨这些 stream 统计，并检查被扣除区间没有夹入真实计算。

扣除规则
固定 2K 构造：Clamp、Arange、LtTensor 的 Broadcast/Less、Fill、SWhere 的 Broadcast/Select，共 7 个设备 kernel；扣除从首 kernel 开始到末 kernel 结束的连续区间。
物理 expert 映射：RemainderTensorScalar 的 Broadcast/FloorMod，共 2 个设备 kernel，同样按连续区间扣除。
完整 MoE 层时延 = 原始层时延 − 本层 2K 构造区间 − 本层 expert 映射区间。
MoE 子模块只扣 expert 映射。真实 TopK、dispatch、GMM、activation、combine 保留。
每步设备适配开销按实采的全部 61 个 attention 层和 58 个 MoE 层求和，不用 58 层代替整模型。
图外 metadata 构造另在未开启 profiler 的相同稳定区间用主机计时测量，扣除首次 D2H 同步结束后到构造返回的时间。
首次 D2H 段可能等待上一轮真实模型执行，不能整段扣除；该段保留，其中实际 D2H/同步开销也保守保留。额外记录该段时间供审计。
校正 TPOT = 客户端未开启 profiler 的实测 TPOT − 每步设备适配区间 − 未开启 profiler 的 metadata 构造时间。
校正吞吐 = 有效 batch × 1000 / 校正 TPOT(ms)，不含 padding，不是含 prefill 的整请求吞吐。
校正值属于时间线扣除估算；不等同于真正移除适配代码后重新测量的反事实结果。原始值和所有扣除项均保留。

A/B 窗口
A = B 组 QKV/q_c/Indexer K 准备 + B 组 cache/QW 准备 + Lightning Indexer B。
B = 合并 q_c/KV 投影 + 完整 batch attention KV/Q 准备 + Q 布局整理 + SFA A。
窗口按连续阶段边界分摊间隙，使各项精确相加；B 窗口扣除夹在 Q 布局和 SFA A 之间的固定 2K 构造区间。
每层新增时延 = 校正拆分完整层时延 − 校正不拆分完整层时延。总时间窗口 = A+B。拆分收益 = 总时间窗口 − 每层新增时延，单位均为 µs/层。
窗口表示当前执行顺序下的设备时间区间，拆分收益表示按窗口计算的潜在重叠收益，不表示已经实现的异步传输重叠或实测 TPOT 改善。
层时延和 A/B 窗口表均为所有稳定 MoE 层样本的平均值，不是单次抽样值。表中各项独立四舍五入，显示值的加总可能有末位差异。

IO 串行 / 理想完全掩盖估算
设 W=A+B（µs/层），L 为需要 IO 的层数。不拆分与拆分每步加载的数据量和纯 IO 总耗时相同，假设每层 IO 耗时恰好为 W。
不拆分串行 IO 层时延 = 不拆分校正完整层时延 + W。
不拆分串行 IO TPOT(ms) = 原不拆分校正 TPOT + L×W/1000；吞吐(token/s) = 有效 batch×1000/新 TPOT。
拆分理想 TPOT = 原拆分校正 TPOT，即所有 IO 均被完整掩盖，无额外调度、同步或计算减速。
理想吞吐提升 = (不拆分串行 IO TPOT / 拆分理想 TPOT − 1)×100%；TPOT 节省 = 不拆分串行 IO TPOT − 拆分理想 TPOT。
用户指定 L=61：全部 61 层均增加相同 IO 耗时 W，包括前 3 个 dense 层。W 使用现有 MoE 层 A+B 平均窗口；这是统一加载耗时假设，未验证 dense 层各自具有同样大小的可用窗口。原 TPOT 中的 dense 计算、LM head、采样等开销保留。
两个窗口在当前时间线上不重合。完全掩盖还要求 A/B 对应加载分别适配各自窗口、数据依赖允许提前加载、缓冲与带宽足够，且 IO 不拖慢计算；仅总加载耗时等于 A+B 并不足以保证这些条件。
以上是固定 IO 预算 W 下的理想上限估算，没有执行带 IO 的新 benchmark。若完全不增加 IO，使用前面的原始对比表。
新增时间直接加到现有整模型 TPOT，不用“平均 MoE 层时延×61”重建 TPOT，也不把“61×每层潜在收益”当作实测端到端节省，因为层时间来自 profiler，而 TPOT 来自未开启 profiler 的采样。
